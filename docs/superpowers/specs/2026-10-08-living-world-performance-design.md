# Elovox — Sub-project 4a: Living-world performance — Design

Status: approved in brainstorming on 2026-10-08 (sections 1–3 approved in chat). Builds on 2b (terrain
documents), 3b (structural collapse), 3d (multi-layer water) and the navigation & workers work.

## 1. Context

Every system now exists, but each was measured alone, in its own small scene. The user's reference
world is **512 × 512** (500 rounded to the 32-block chunk). On 2026-10-08 the plain `world` scene at
`?size=512` was measured on the desktop (production build, WebGPU, Edge headed, 1920 × 889):

| Camera distance | fps median | fps p5 | CPU frame ms (median) | GPU ms | draws |
|---:|---:|---:|---:|---:|---:|
| 70 | 76 | 60 | 5.5 | 1.3 | 680 |
| 200 | 75 | 63 | 7.3 | 1.4 | 1,072 |
| 400 | 75 | 62 | 8.1 | 1.1 | 1,241 |

fps sits at the monitor's ~75 Hz in every view. The zoomed-out draw-bound problem recorded in 2a
(33 fps, ~3,800 draws) belongs to the 1024 world. Rendering an idle 512 world is therefore not the
bottleneck. What has never been measured is the **game load on top of it**: water, collapse and units
running at once.

| Topic | Decision |
|---|---|
| Goal | The living 512 × 512 world (water, collapse, dozens of units at once) at ≥ 60 fps |
| Reference machine | This desktop (Ryzen 5 5600, its GPU, Edge, production build). The laptop is out of scope |
| Approach | **Measure first, two phases in one sub-project**: phase 1 builds the scene and the benchmark and takes a baseline; a decision checkpoint with the user picks the optimizations; phase 2 applies them one at a time, each measured. Rejected: optimizing the known suspects up front (BatchedMesh, off-thread water apply, unit instancing) before knowing what the 512 world actually misses; and two separate sub-projects (same work, more ceremony) |

## 2. Scope and success criteria

### In scope

- A sandbox scene `?scene=living` that runs every system together on a 512 × 512 × 128 terrain.
- A repeatable benchmark of that scene, phase by phase, plus a light functional e2e.
- A baseline, a decision checkpoint, then targeted optimizations until the targets hold.

### Out of scope

- New game rules or behaviour of any system. When a set piece does not fit a current limit
  (`maxOrders`, concurrent searches, collapse caps), the scene's configuration changes, not the engine.
- The 1024 world, the laptop, the terrain-editor and regeneration budgets (2b/2c follow-ups).

### Success criteria

Per benchmark phase (§4), on the reference machine, the worse of two runs:

- **fps p5 ≥ 60**
- **sim tick p95 ≤ 10 ms**
- **main-thread water apply p95 ≤ 4 ms**

Plus: every existing unit and e2e suite still passes, including water state hashes and the units'
deterministic replay, and nothing visible changes without a checkpoint with the user.

## 3. The scene `?scene=living`

### Terrain

A new document `apps/sandbox/src/terrain/living.terrain.json`, 512 × 512, generated by
`terrainGenerator` (sim worker and gen worker, as the `terrain` scene does). It reuses the showcase's
kinds of ops at the smaller scale: mountains, hills, a river, a lake, the sea along one edge, caves.
It adds **four `flatten` plateaus** whose heights are known constants exported from
`apps/sandbox/src/scenes/living.ts`; the set pieces stand on them.

### Set pieces, built by commands after load

Built with `fillRegion` / `setBlock` once the world is ready, so they pass through the same hooks as
any edit (water, gravity, collapse, light, workers' invalidation). No scene generator and no engine
change.

1. **Dammed reservoir** on a high plateau: stone walls, water inside, filled and settled before
   measuring. *Breach* cuts a gap in the downhill wall; the water runs down the slope to the river.
2. **Collapsing structure** on another plateau: a tower and a walkway of `structural_planks`
   (the collapse option is on). *Collapse* cuts the tower's base.
3. **Work site**: a hillside for a tunnel (`workDig`), the river for a bridge (`workBuild`), open
   ground for a wall (`workBuild`).
4. **50 units** (`unitSpawn`) with tools and stock: three crews (tunnel, bridge, wall) and a group
   that moves between plateaus (`unitMove`).

The scene's worker options extend `WORKER_OPTIONS` with the materials the terrain uses.

### Script

`window.__elovox.living` exposes `setup()`, `startWork()`, `breach()`, `collapse()` and
`moveGroup()`, as `flood` and `collapse` do. The HUD gets buttons for the same events, so the user can
replay by hand what the benchmark does. Command lists live in `scenes/living.ts` as pure functions
(testable without a browser, like `scenes/flood.ts`).

## 4. Benchmark and metrics

`apps/sandbox/e2e/living-bench.spec.ts`, skipped unless `BENCH_LIVING=1`. Run on the production
build (`E2E_PREVIEW=1`), Edge headed (`E2E_CHANNEL=msedge`, `--headed`), viewport 1920 × 889,
`?scene=living&gpu`. A fixed script with one measurement window per phase:

| Phase | What happens | Window | Camera |
|---|---|---:|---|
| 1. Idle | world loaded, reservoir full, no work | 10 s per camera | default (70) and far (400) |
| 2. Work | 50 units on the work site, the group moving | 30 s per camera | default and far |
| 3. Dam | `breach()` while the units keep working | 45 s | far, valley and river in view |
| 4. Collapse | `collapse()` while the water still runs | 20 s | default, facing the tower |

Per phase it records:

- **fps** median, p5 and min, from `requestAnimationFrame` intervals
- **CPU frame** `frameMs` median and p95; **GPU** `gpuMs`
- **sim tick** p95 and max, from the `tick` event
- **water apply** `waterApplyMs` p95 and max
- **counters**: draws, shadow casters, decoration instances, units by state, active searches,
  collapse fragments, active water columns

Output: a JSON attachment in the Playwright report, also saved as
`docs/superpowers/research/2026-10-08-living-baseline.json`. Every later comparison uses the same
format. `BENCH_ASSERT=1` fails the run on any missed target; without it the run only records.

Noise rules: two runs per measurement, the worse one counts (as the collapse bench does); no build or
tests running alongside. fps is capped at ~75 by the monitor, so before/after comparisons rely on CPU
frame, tick and water apply, not fps alone.

`apps/sandbox/e2e/living.spec.ts` (always runs, no timing): the scene loads without console errors,
units start working, the breach wets the valley, the tower falls.

## 5. Decision checkpoint and phase 2

### End of phase 1

The baseline goes to the user as a per-phase table: what missed and by how much, where the time goes
(a Chrome DevTools profile of the main thread and of the sim worker for each missing phase), and
candidate optimizations with their expected gain. The user picks; the picks become an **addendum to
the plan** with phase-2 tasks. If nothing misses, the sub-project ends with the scene and the
benchmark delivered.

### Rules for phase 2

1. An optimization enters only when the measurement points to it; each task names the phase and the
   metric it attacks.
2. Before and after on the same benchmark; the commit message records both. No measured gain → the
   change is reverted.
3. No behaviour change: existing suites stay green, including water state hashes and the units'
   replay. A visible change becomes a checkpoint with the user.
4. One optimization at a time, so each gain has a known cause.
5. Done when every target holds in every phase, or the user stops and the open misses are recorded.

Known candidates, entered only if measured: chunk drawing in batches (BatchedMesh / multi-draw);
water apply off the main thread or incremental; instanced or distance-limited animated unit models;
sim work spread across ticks.
